## The problem

**Situation.** Authorise every agent tool call against user intent, data sensitivity and least privilege in real time, blocking unsafe or out-of-scope actions. The system has to run in under 100 milliseconds, inside these limits: Under 20 ms per tool call, Deterministic policy where required and Audit of every decision.

**Why it is hard.** The obvious approach is agent inherits user's full permissions, and it fails because a hijacked agent should not have full access. The second trap is in "Policy": the real signal is deterministic policy engine with ML as advisor, while teams usually reach for mL-only authorisation.

**Scale and stakes.** At 10 million users this is about 60.0M model-touching events a day, 694 requests per second on average and 4.2K at peak, at an estimated $8.28M a month. A mistake is expensive in the way task completion rate measures it.

**What success looks like.** Offline: Unsafe action block rate and benign pass rate on red-team traces and Decision latency. Online: Blocked unsafe actions and Task completion rate. The launch is judged on "Blocked unsafe actions" while "Task completion rate" must not get worse.

## Objective, loss and constraints

**Business objective.** Authorise every agent tool call against user intent, data sensitivity and least privilege in real time, blocking unsafe or out-of-scope actions.

**Training objective.** `\mathcal{L}=\mathrm{BCE}(\text{unsafe},p)+\lambda\,\mathrm{Latency}`

**Loss variables**

| Symbol | Meaning |
|---|---|
| \mathcal{L} | The loss: the single number training tries to make as small as possible. Lower means the model fits the data and respects the extra terms better. |
| \mathrm{BCE} | Binary cross-entropy: the standard loss for yes/no predictions. It is large when the model gives a low probability to what actually happened. |
| \text{unsafe} | The label: 1 if a requested tool action is unsafe, 0 if safe. |
| p | The model's predicted probability that the outcome is positive (between 0 and 1). |
| \lambda | Penalty weight: how strongly the added term counts against the main objective. A larger value enforces that term harder, at some cost in fit. |
| \mathrm{Latency} | Penalty for the extra time the guardrail adds to each tool call. |

**Hard constraints**

- Under 20 ms per tool call
- Deterministic policy where required
- Audit of every decision
- Human approval for high-risk

## The approach in one paragraph

Start with static allow-lists of tools per agent. Then earn the move to policy decision point combining capability scopes, intent-consistency model and sensitivity checks with human approval for high-risk calls, and only if it beats the baseline on Unsafe action block rate and benign pass rate on red-team traces and Decision latency after variance.

**Moves**

| Move | Detail |
|---|---|
| Build the model around Intent-action consistency | Does action match user request. Hijack detection. Guard against: intent model. |
| Add Data sensitivity of arguments | Classification of data in args. Exfiltration risk. Guard against: dLP. |
| Add Action reversibility tier | Read, write, delete, external send. Risk. Guard against: metadata. |
| Run it as one pipeline | Agent tool call (SDK hook), Capability check (token scopes), Intent-consistency model (small LLM or encoder), Sensitivity classifier (DLP) and Policy decision (OPA rules), with Human approval and Decision audit off the critical path. |
| Optimise the right thing | The objective weighs binary cross-entropy: the standard loss for yes/no predictions. It is large when the model gives a low probability to what actually happened, so the model is trained on the cost of the decision and not on a generic score. |
| Handle legitimate multi-step task looks like out-of-scope action | Task-plan declaration and scoped delegation. |

**Deliberately not doing**

- Tool name alone: insufficient.
- Agent confidence: uncalibrated.

**How the approach is proven**

Prove it offline on Unsafe action block rate and benign pass rate on red-team traces and Decision latency using time-ordered splits, then online on "Blocked unsafe actions" with "Task completion rate" as the guardrail. Watch for: Red-team traces generated by builders and Ignoring multi-agent delegation chains.

## Baseline and production design

- **Baseline (build this first):** Static allow-lists of tools per agent.
- **Production design:** Policy decision point combining capability scopes, intent-consistency model and sensitivity checks with human approval for high-risk calls.

## Why AI, and why this kind

**Why AI.** Authorise every agent tool call against user intent, data sensitivity and least privilege in real time, blocking unsafe or out-of-scope actions. The evidence that separates good from bad outcomes (Intent-action consistency, Data sensitivity of arguments, Action reversibility tier) is high-dimensional and shifts over time, which a fixed threshold cannot track.

**Why not rules.** Rules of the form "agent inherits user's full permissions" are what teams reach for first, and they fail because A hijacked agent should not have full access. Rules stay as the policy layer around the model (limits, compliance, safe defaults) but cannot rank the cases inside them.

**Why this paradigm.** The task is multi-step with variable paths and tool use that a fixed workflow cannot express, provided tools are typed, permissioned and verified. Here the production design is: Policy decision point combining capability scopes, intent-consistency model and sensitivity checks with human approval for high-risk calls.

**Options weighed**

| Option | Verdict | Reason |
|---|---|---|
| Rules and thresholds only (status quo) | rejected | Cannot capture the interactions among Intent-action consistency, Data sensitivity of arguments, Action reversibility tier and decays as behaviour changes; kept as the policy layer and the last rung of the degradation ladder. |
| Baseline: Static allow-lists of tools per agent | fallback | Sets the cost floor, gives the benchmark every challenger must beat and stays deployed as the in-process fallback. |
| Policy decision point combining capability scopes, intent-consistency model and sensitivity checks with human approval for high-risk calls | chosen | Meets the 80 ms envelope at $4.60 per 1,000 decisions and exposes the signals the baseline cannot use. |
| Fully autonomous agent with broad tools | later | Unsafe without earned autonomy; start at read-only and promote by evidence |
| LLM or agent as the decision maker | rejected | This is already an LLM system; the question is how much autonomy to grant, which the autonomy ladder answers |
| Buy a vendor model end to end | later | Reasonable for a first release without labels; integrate the vendor score as a feature and keep the policy and ledger in-house. |

**Revisit the decision when**

- Label volume or signal changes enough that a fully autonomous agent with broad tools beats the champion by a pre-agreed margin on the frozen holdout and every protected slice
- The latency or cost envelope moves (a looser p99 or cheaper serving makes a heavier tier affordable; a tighter one forces a lighter cascade)
- The guardrail metric (Blocked unsafe actions) breaches for two consecutive matured-label windows despite retraining
- A new regulatory or contractual requirement changes what must be explained, localised or approved (Breach notification timelines)
- The decision starts to change the data it learns from (selection bias grows), which calls for exploration or counterfactual evaluation

## Risks to name now

- Evaluation trap: Red-team traces generated by builders.
- Evaluation trap: Ignoring multi-agent delegation chains.
- Legitimate multi-step task looks like out-of-scope action: agent blocked unnecessarily.
- Policy engine outage: agents either unsafe or unavailable.
