## The problem

**Situation.** Detect a customer-impacting network fault, match it to an approved runbook, propose or apply a fix through the orchestrator and verify recovery, so time to restore falls without unsafe changes reaching the live network. The system has to run interactively, within a few seconds, inside these limits: Only pre-approved change templates can be executed and anything above a risk threshold needs human approval, Every action has a rollback and an automatic stop if service KPIs worsen and The agent cannot touch lawful-intercept or core security functions.

**Why it is hard.** The obvious approach is free-form commands generated by the model, and it fails because a model that can type any command can take down a region. The second trap is in "Trigger": the real signal is a correlated incident with confirmed service impact, while teams usually reach for every raw alarm.

**Scale and stakes.** At 10 million users this is about 1.5M model-touching events a day, 17 requests per second on average and 104 at peak, at an estimated $210.9K a month. A mistake is expensive in the way incidents resolved without escalation measures it.

**What success looks like.** Offline: Share of incidents with a correct runbook proposed, Rollback correctness in replay and Rate of proposals blocked by guardrails. Online: Mean time to restore for covered fault classes, Incidents resolved without escalation and Change-induced outages. The launch is judged on "Mean time to restore for covered fault classes" while "Incidents resolved without escalation" must not get worse.

## Objective, loss and constraints

**Business objective.** Detect a customer-impacting network fault, match it to an approved runbook, propose or apply a fix through the orchestrator and verify recovery, so time to restore falls without unsafe changes reaching the live network.

**Training objective.** `\mathcal{L}=-\sum_t\log p_\theta(y_t\mid y_{<t},x)+\lambda\,\mathrm{BCE}(\hat{p},y)`

**Loss variables**

| Symbol | Meaning |
|---|---|
| \mathcal{L} | The loss: the single number training tries to make as small as possible. Lower means the model fits the data and respects the extra terms better. |
| \sum_t | Sum: add up the term for every value of the index written under it (all examples, time steps, classes and so on). |
| \log | Natural logarithm. It turns probabilities into log-likelihood terms that add up and punish confident mistakes heavily. |
| p_\theta | The language model's probability of the next token y_t, given the earlier tokens and the context written after the bar. (one value per time step or token t and forecast step h) |
| y_t | The true outcome the model is trained to predict: a label such as 1 for positive and 0 for negative, or a measured value. (one value per time step or token t) |
| \mid | 'Given': what follows is the information the probability or prediction is conditioned on. |
| y_{<t} | All tokens before position t: the text the model has already read or generated. (one value per time step or token t) |
| x | The input features describing one example (what the model sees). |
| \lambda | Penalty weight: how strongly the added term counts against the main objective. A larger value enforces that term harder, at some cost in fit. |
| \mathrm{BCE} | Binary cross-entropy: the standard loss for yes/no predictions. It is large when the model gives a low probability to what actually happened. |
| \hat{p} | The model's estimated probability, after calibration where one is applied. |

**Hard constraints**

- Only pre-approved change templates can be executed and anything above a risk threshold needs human approval
- Every action has a rollback and an automatic stop if service KPIs worsen
- The agent cannot touch lawful-intercept or core security functions
- Plans and tool calls logged for audit
- Handles 3M alarms per day with a first proposal inside 20 s

## The approach in one paragraph

Start with a rules engine that maps correlated alarm patterns to runbooks and opens a ticket for an engineer, because it is auditable and shows how much remediation can be automated. Then earn the move to a planner agent over a read-only tool set for topology, KPIs and runbooks and a separate executor limited to approved templates, with an approval gate by blast radius, a post-action KPI verifier and automatic rollback, and only if it beats the baseline on Share of incidents with a correct runbook proposed and Rollback correctness in replay after variance.

**Moves**

| Move | Detail |
|---|---|
| Build the model around Correlated incident severity | Number of impacted subscribers and services behind the alarm group. Targets the agent at real impact. Guard against: computed from topology at alarm time. |
| Add Runbook match score | Similarity of incident symptoms to the symptoms recorded in each approved runbook. Chooses the template. Guard against: runbooks must be versioned with the topology they were written for. |
| Add Blast radius estimate | Count of cells and customers reachable from the target element. Sets the approval tier. Guard against: use the live inventory not a stale snapshot. |
| Run it as one pipeline | Alarm intake and correlation (stream processor), Incident enrichment (topology and inventory lookup), Runbook retrieval (vector index over approved runbooks), Plan proposal (planner agent with tool use), Approval gate (risk tiers and maker-checker), Execution (orchestrator templates) and KPI verification and rollback (closed-loop check), with Audit log off the critical path. |
| Optimise the right thing | The objective weighs sum: add up the term for every value of the index written under it (all examples, time steps, classes and so on), so the model is trained on the cost of the decision and not on a generic score. |
| Handle alarm storm during a major outage | Incident-level locking so one plan owns a topology slice at a time. |

**Deliberately not doing**

- Alarm text wording: vendor phrasing differs for the same fault.
- Operator on shift: does not change the right fix.
- Ticket priority typed by hand: inconsistent across teams.

**How the approach is proven**

Prove it offline on Share of incidents with a correct runbook proposed, Rollback correctness in replay and Rate of proposals blocked by guardrails using time-ordered splits, then online on "Mean time to restore for covered fault classes" with "Incidents resolved without escalation" as the guardrail. Watch for: Letting the model compose raw commands, Counting alarm closure as recovery and Training on tickets that record the fix not the cause.

## Baseline and production design

## Why AI, and why this kind

**Why AI.** Detect a customer-impacting network fault, match it to an approved runbook, propose or apply a fix through the orchestrator and verify recovery, so time to restore falls without unsafe changes reaching the live network. The evidence that separates good from bad outcomes (Correlated incident severity, Runbook match score, Blast radius estimate) is high-dimensional and shifts over time, which a fixed threshold cannot track.

**Why not rules.** Rules of the form "free-form commands generated by the model" are what teams reach for first, and they fail because A model that can type any command can take down a region. Rules stay as the policy layer around the model (limits, compliance, safe defaults) but cannot rank the cases inside them.

**Why this paradigm.** The task is multi-step with variable paths and tool use that a fixed workflow cannot express, provided tools are typed, permissioned and verified. Here the production design is: A planner agent over a read-only tool set for topology, KPIs and runbooks and a separate executor limited to approved templates, with an approval gate by blast radius, a post-action KPI verifier and automatic rollback.

**Options weighed**

| Option | Verdict | Reason |
|---|---|---|
| Rules and thresholds only (status quo) | rejected | Cannot capture the interactions among Correlated incident severity, Runbook match score, Blast radius estimate and decays as behaviour changes; kept as the policy layer and the last rung of the degradation ladder. |
| Baseline: A rules engine that maps correlated alarm patterns to runbooks and opens a ticket for an engineer, because it is auditable and shows how much remediation can be automated | fallback | Sets the cost floor, gives the benchmark every challenger must beat and stays deployed as the in-process fallback. |
| A planner agent over a read-only tool set for topology, KPIs and runbooks and a separate executor limited to approved templates, with an approval gate by blast radius, a post-action KPI verifier and automatic rollback | chosen | Meets the 2500 ms envelope at $4.69 per 1,000 decisions and exposes the signals the baseline cannot use. |
| Fully autonomous agent with broad tools | later | Unsafe without earned autonomy; start at read-only and promote by evidence |
| LLM or agent as the decision maker | rejected | This is already an LLM system; the question is how much autonomy to grant, which the autonomy ladder answers |
| Buy a vendor model end to end | later | Reasonable for a first release without labels; integrate the vendor score as a feature and keep the policy and ledger in-house. |

**Revisit the decision when**

- Label volume or signal changes enough that a fully autonomous agent with broad tools beats the champion by a pre-agreed margin on the frozen holdout and every protected slice
- The latency or cost envelope moves (a looser p99 or cheaper serving makes a heavier tier affordable; a tighter one forces a lighter cascade)
- The guardrail metric (Mean time to restore for covered fault classes) breaches for two consecutive matured-label windows despite retraining
- A new regulatory or contractual requirement changes what must be explained, localised or approved (Telecom licence conditions on availability and outage reporting)
- The decision starts to change the data it learns from (selection bias grows), which calls for exploration or counterfactual evaluation

## Risks to name now

- Evaluation trap: Letting the model compose raw commands.
- Evaluation trap: Counting alarm closure as recovery.
- Alarm storm during a major outage: the agent proposes many overlapping fixes.
- Stale inventory: the plan targets the wrong element.
